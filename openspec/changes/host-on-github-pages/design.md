# Design

## Context

See proposal.md for motivation. Current state that shapes the approach:

- `src/api/storage.js` loads `public/data/games.json` and `journal.json` by URL. It caches every edit in localStorage with a dirty flag, and on Save POSTs to a Vite dev-server plugin, falling back to downloading the files.
- `src/api/igdb.js` reaches Twitch and IGDB through Vite dev proxies, using `VITE_IGDB_CLIENT_ID` and `VITE_IGDB_CLIENT_SECRET`. Vite inlines `VITE_*` variables into the bundle, so any production build would publish the secret.
- IGDB is called on five endpoints: `/v4/games`, `/v4/game_time_to_beats`, `/v4/screenshots`, plus the Twitch token exchange. HowLongToBeat is reached via `/hltb-api`, which has no proxy configured, so it already fails.
- Data is small (about 250 KB total) and well structured: each game has a numeric `id`, and the journal is an object keyed by game id holding arrays of entries, each with its own `id`.
- The repository is public. The owner edits from more than one device.

## Goals / Non-Goals

**Goals:**
- A single data path used both on Pages and in local dev, so behaviour is the same everywhere.
- Each save is one atomic commit covering both data files.
- No secret is ever present in the frontend bundle or the repository.
- Concurrent edits from two devices never silently lose data.

**Non-Goals:**
- Real confidentiality of the data (the repository stays public).
- Offline-first editing across long periods. Edits made offline are kept locally and saved when back online, but there is no queue of separate commits.
- Multiple users, or any user other than the repository owner.
- HowLongToBeat, in any form.

## Decisions

### Data files move from `public/data/` to `data/` at the repository root
Files under `public/` are copied into the Pages build and served at a predictable URL. Moving them out means the site never serves the data, and data-only commits don't need a rebuild.
*Alternative:* keep `public/data/` and load through the API anyway. Rejected because the files would still be published with each deploy.

### Load and save through the GitHub Git Data API, not the Contents API
A save writes both files in one commit: create blobs, create a tree on the base commit's tree, create a commit whose parent is the base commit, then update `refs/heads/main` without force. If another device has pushed, the ref update fails because it is not a fast-forward. That failure is the conflict signal. Loading reads the branch head commit and fetches both files at that commit.
*Alternative:* the Contents API (`PUT` per file with its blob `sha`). Simpler, but saving two files takes two commits, and a failure between them leaves the repository half-updated. The Git Data API costs about four extra requests per save, which is negligible.

### The merge base is the last commit this device loaded or saved
Each device stores, in localStorage: the base commit sha, the base content of both files, and its current local content. This replaces the old dirty flag: local content differing from base means unsaved.

### Three-way merge rules
On a conflict, fetch the new head (remote), then merge base, local and remote:

- **Games**, keyed by `id`:
  - Present only locally (added here), or only remotely (added there): keep.
  - Deleted on one side and unchanged on the other: delete.
  - Deleted on one side and modified on the other: keep the modified version, so no edit is lost.
  - Modified on both sides: merge field by field. A field changed on only one side takes that side's value. A field changed on both sides takes the local value, since the device saving now holds the most recent action. Array fields such as `tags` or `dlc` are compared as whole values.
  - Order: follow the remote order, then append games added locally.
- **Journal**, keyed by game id, then by entry `id`: the same add, delete and modify rules per entry. Entries keep their existing sort.

After merging, save again on top of the new head. If a second conflict happens, repeat up to three times, then show an error state without discarding local content.
*Alternative:* last write wins, which silently drops the other device's edits. Or prompting the user on every both-sides conflict, which is noisy for a single owner. Per-field timestamps were considered for "newer wins", but the data has no such timestamps and adding them is not worth it here.

### Autosave timing
Save 5 seconds after the last edit. Also save immediately, best-effort, when the page becomes hidden. When the page becomes visible, check the head commit. If it moved and there are no local changes, reload silently. If there are local changes, merge right away. A small status indicator in the header replaces the Save button, with states such as Saved, Saving, Unsaved, Offline and Error.
Commit messages summarise what changed, e.g. `Update library: edit Pragmata, add Hades`. They are generated by diffing base against local. Commits are authored as the token's owner.

### Sign-in uses a fine-grained token, stored in localStorage
The owner creates a fine-grained personal access token restricted to this repository, with Contents read and write and Metadata read. On sign-in the app calls `GET /repos/{owner}/{repo}` and requires `permissions.push === true`. The token is kept in localStorage on that device. Sign-out clears the token and all cached data.
*Alternative:* GitHub OAuth. It needs a server-side code exchange, which means another backend endpoint and an OAuth app, for no benefit to a single user.

### IGDB lookups run in a GitHub Actions workflow, not in the app
IGDB can't be called from a browser: it blocks cross-site requests, and its client secret would be published. Rather than host a proxy, the owner adds IGDB-backed games through a `workflow_dispatch` workflow, **Add game from IGDB**. Its form takes title, system, status, ownership, an optional release year, an optional IGDB ID, and a preview-only switch. The workflow runs `scripts/add-game.js` with Node and no dependencies, using `IGDB_CLIENT_ID` and `IGDB_CLIENT_SECRET` from repository secrets.

Matching uses only what the owner entered, and every IGDB query is limited to the IGDB platform for the chosen system. Results from other systems are never considered. A system with no IGDB platform ("Other") is searched unfiltered.
1. If an IGDB ID is given, use that game directly.
2. **First pass:** IGDB text search for the title, 20 results, excluding mods, episodes and seasons.
3. **Wider pass**, only if the first pass has no confident match: IGDB text search with 200 results, plus a name-contains query requiring every significant word of the title (up to five words), with 200 results. Results are combined and de-duplicated.
4. A match is **confident** when it is an exact title (ignoring case, punctuation and accents), or when exactly one result contains every word the owner typed, ignoring "the", "of", "a", "an" and "and". Between several exact titles, a release year equal to the one entered decides, then IGDB's order. A release year also narrows the every-word results.
5. With no confident match after both passes, fail the run without changing the library. The job summary lists the closest results on that system with their IGDB IDs, so the owner can re-run with an ID.

The game is built from the owner's choices (system, status, ownership) plus IGDB's details: title, cover, release year, genre, franchise, developer, critic score, modes, perspectives, themes, DLC, time to beat, and bundled games. If the library already has the game (same `igdbId`, or the same title and system), the run refreshes its IGDB details and keeps the owner's fields: status, ownership, rating, notes, and the done-states of DLC and included games.

The script commits `data/games.json` with the same Git Data API client and three-way merge as the app, authenticated with the workflow's `GITHUB_TOKEN` (`contents: write`). If the app saved in the meantime, the merge combines both changes. Commits made with `GITHUB_TOKEN` don't trigger other workflows, so there is no Pages rebuild. The app picks up the new game when its tab next regains focus. A job summary shows the chosen match and the runners-up.

The IGDB mapping code (`PLATFORM_ID_MAP`, genre and platform maps, field extraction) moves from `src/api/igdb.js` to `scripts/igdb.js`. The app no longer imports it.

Searching other platforms when the chosen one has no result was tried first. It was dropped because the owner wants results limited to the system they picked. Accepting IGDB's top result when nothing matched exactly was also dropped: it could silently add the wrong game.

*Alternatives:* An IGDB proxy on Deno Deploy (shutting down in 2027) or Vercel would keep live search in the form, but it adds a hosting service to maintain. A workflow triggered automatically by every save was considered. It was rejected because the owner wants the lookup driven by the options they enter, and to keep it out of the everyday editing flow. Calling IGDB from the browser is not possible (CORS and the client secret).

### Frontend configuration
Build-time values contain no secrets: `VITE_GITHUB_OWNER`, `VITE_GITHUB_REPO` and `VITE_GITHUB_BRANCH` (default `main`). Vite `base` is `/backlogtracker/` for production builds and `/` in dev. The app has no IGDB configuration.

### Local dev uses the same paths
`npm run dev` talks to the real GitHub repository with the signed-in token. The add-game script can also be run locally with `node scripts/add-game.js` (see the README). The `save-data` plugin and the `/twitch-token` and `/igdb-api` dev proxies are removed.

### Pages deploy
A GitHub Actions workflow builds on pushes to `main` and deploys with `actions/deploy-pages`. It uses `paths-ignore: ['data/**', 'openspec/**']` so autosave commits don't trigger deploys. The `VITE_*` values come from repository variables, not secrets, since none of them are sensitive.

### HowLongToBeat removal
Delete `src/api/hltb.js`, the HLTB fallback in `enrichGame`, and the fallback in `AddGameModal`. `timeToBeat` is filled only from IGDB `game_time_to_beats`, or by hand.

## Risks / Trade-offs

- [The token sits in localStorage, so XSS could steal it] → The token is limited to this one repository with Contents write only. The app loads no third-party scripts. Sign-out clears it, and the token can be revoked on GitHub at any time.
- [The data is still public in the repository] → Accepted by the owner. The gate only hides data from visitors to the site. Documented in the README.
- [GitHub API rate limits: 5,000 requests per hour per token] → At about 6 requests per save plus a head check on focus, this is far below the limit at human editing speed. The debounce keeps the save count low.
- [Many small commits in history] → Debounced batches and descriptive messages keep history readable. This replaces the manual "dump" commits.
- [Edits on both sides of one field: local wins, so the other device's value is lost] → Rare for a single person. The lost value remains in git history.
- [The page closes before the debounced save fires] → Local content persists in localStorage and saves on next open, merging if needed.
- [Adding a game from IGDB takes a workflow run (about 30 to 60 seconds) and happens outside the app] → Accepted, in exchange for no extra service. Manual add in the app stays instant, and the form in the Actions tab works from a phone.
- [The chosen IGDB match is wrong] → Exact-title and year ranking, platform limit, a preview-only mode, and an IGDB ID override. The summary always shows what was picked.

## Migration Plan

1. Move `public/data/*.json` to `data/` in the same commit that switches the app to the API.
2. On first load of the new app, if the old `backlog_dirty` flag is set, treat the old localStorage content as local, with the freshly loaded head as base. The normal merge then saves it. Remove the old keys afterwards.
3. Owner setup, documented in the README: create the fine-grained token; add `IGDB_CLIENT_ID` and `IGDB_CLIENT_SECRET` as Actions repository secrets; set the repository variables; set Pages source to GitHub Actions.
4. Rollback: revert the app commits. The data format is unchanged, so moving `data/` back to `public/data/` restores the old flow.
